# モバイルオンボーディング

## 概要（発動条件）

モバイルアプリの初回オンボーディングを設計し、実装まで進める。ページ形式のオンボーディングで、次の4つを達成する。

- 何のためのアプリかがわかること
- 基本的な使い方がスリーステップでわかること
- ワクワクすること
- 早くアプリを使いたいと思わせること

「オンボーディングを作って」「初回体験を設計して」「このアプリの導入画面を改善して」「このアプリの最初の流れをテンポよくして」など、モバイルアプリの初回導入の依頼に使う。Webサイトのランディングページ、既存ユーザーのチュートリアル、設定画面そのものには使わない。特定の1画面だけの修正依頼は、その画面の範囲に限定する。

コンセプトを深く理解してからページを作る。アプリの内容やコンセプトを読み取らずにページ案を作らない。concept-driven-ux スキルと連携する場合は、コンセプトの読み取りと最終照合をそちらと共有し、このスキルではオンボーディングのページ設計と実装に集中する。

## 絶対のルール（1ページ1主張）

- 1ページは1つの主張だけを載せる。1画面で言いたいことを2つ以上載せない。
- ページ枚数はいくら多くなってもよい。詰め込むより割ることを選ぶ。
- 「〜して、〜もできます」は2つの主張なので分割する。分割できない場合は、そのページの主役を1つに決め、もう一方は別のページへ移すか削る。
- 見出しは主張そのものを1行で書く。見出しを読めばそのページの主張がわかる状態にする。
- 補足文は主張を支える1〜2行まで。段落で説明しない。詳しい説明が必要なら別ページにするか、アプリ本体のヘルプへ逃がす。
- 質問とその結果は、必ず別ページにする。質問のページには質問と選択肢だけを置き、結果（マッチ宣言、診断の返し、タイプ表示）は次のページで単独で示す。質問と結果を同じ画面に同居させることは、主張が2つになるため禁止する。

このルールはオンボーディング全体の土台であり、ページ数・テンポ・演出の都合で緩めない。

## 始める前にコンセプトを深く理解する

ページ案を作る前に、対象アプリの内容とコンセプトを読み取る。

- 対象アプリのリポジトリや設計資料、README、コンセプト文、主要画面と初回の利用の流れを確認する。
- 次を短く記録する。事実、設計上の仮説、未確認事項を分ける。
  - コンセプト：［誰］が［どんな場面］で［何をする］ことで［どんな状態や気持ちになる］体験
  - アプリが解決する困りごとと、解決後のいちばんの変化
  - 最初の小さな成功（ユーザーが最初に「できた」と感じる瞬間）
  - 使う場面の頻度と、初回と反復利用で変わること
  - 競合や類似アプリと違う点
- コンセプトが一文で言えない場合は、ページ案へ進まず、資料から候補を1〜3案作って利用者に確認する。推測のコンセプトでページを作らない。
- アプリの内容を読み取れない資料しかない場合は、読み取れた範囲と未確認の範囲を明示し、ページ案は仮説として扱う。
- 既存のオンボーディングがある場合は、現行のページ構成と主張を1ページずつ読み取り、このスキルの4つの達成条件で評価してから改善対象を決める。

## 4つの達成条件を先に決める

設計の前に、今回のオンボーディングで満たす4条件を具体化して記録する。

- 何のためのアプリか：ユーザーが自分の言葉で言い直せる一文を決める。
- 基本的な使い方（スリーステップ）：本体の最初の操作をちょうど3つに分ける。4つ以上ある場合は統合するか、初回に要らない操作をオンボーディングから外す。3つに分けられない場合は、その理由と代わりの分け方を利用者へ確認する。
- ワクワクする瞬間：ユーザーが「やってみたい」と思う場面を、オンボーディングのどのページに置くか決める。最後だけに置かず、途中の山場としても配置する。
- 早く使いたい：最後のページで「始める」を押した先が、説明の続きではなく本体の最初の小さな成功に直結する状態にする。

## ページの地図を作る

主張の棚卸しからページ構成を決める。ページの地図は、ページごとの主張と役割とアニメーションを並べた表として作る。アニメーションの欄には、そのページの主役のアニメーションと、その意味（何を目立たせ、何を伝えるか）を書く。意味を書けないアニメーションは地図に入れない。地図の様式と記入例は [ページ地図のテンプレート](references/page-map-template.md) を使う。詳細な型は [ページのパターン集](references/page-patterns.md) を使う。

- ページの役割は次の9種から選ぶ。1ページに役割を2つ与えない。
  - フック：共感や驚きで引き込む
  - 選択：ユーザーの悩みや希望を選ばせる（1ページ1問）
  - マッチ：選んだ悩みや希望を受けて「そんなあなたにはこのアプリがぴったり」と返す（1ページ1宣言）
  - アイデンティティ：何のためのアプリかを示す
  - 価値：使うと何が変わるかを示す（1価値1ページ）
  - ステップ：基本的な使い方の1ステップを示す（1ステップ1ページ、ちょうど3ページ）
  - インタラクション：試し操作など、その他の選択や回答をさせる
  - 期待：ワクワクの山場を示す
  - 接続：本体の最初の行動へ渡す
- 並び順の基本は、フック → 選択（悩み・希望） → マッチ → アイデンティティ → 価値（1〜3ページ、選んだ悩みに対応する価値から） → ステップ（3ページ） → インタラクション（途中に散らす） → 期待 → 接続 とする。アプリの性格で順番を変えてよいが、選択とマッチの順序は入れ替えない。詳しくは「悩み・希望を選ばせて、ぴったりで返す」を使う。
- 権限の許可やアカウント作成、通知の設定は、価値が伝わった後へ置く。1ページ1目的とし、システムのダイアログを出す前に「なぜ必要か」を1行で示す。価値の前に許可を求めない。
- インタラクションのページは、オンボーディングの途中に散らす。最後にまとめて置かない。
- ページ数の目安は10〜15ページとする。標準フロー（フック、選択1〜2、マッチ、アイデンティティ、価値1〜3、ステップ3、試し操作とその結果、期待、接続）を数えた実数に基づく目安である。これより少ない場合は主張が詰め込まれていないか確認し、これより多い場合は主張の削減を先に検討する。枚数自体の上限は設けないが、総時間の目安（「文言とテンポの仕上げ」）を超える場合は、ページを統合せず主張を削る。

## 悩み・希望を選ばせて、ぴったりで返す

オンボーディングの標準の流れとして、ユーザーの悩みや希望を選ばせ、その答えに「そんなあなたにはこのアプリがぴったり」と返す一連のページを必ず入れる。見せるだけの説明から「自分のことだ」と感じさせる転換点であり、引き込みの核として扱う。対象アプリに特定できる悩みや希望がどうしても無い場合だけ、理由を記録して省略できる。

### 選択のページ（悩み・希望）

- 質問は1ページに1つだけ置く。質問の文面はユーザーの日常の言葉で書く（例：いちばん困っているのはどれですか、いちばん叶えたいのはどれですか）。
- 選択肢は3〜4個とする。1つ1つが具体的な場面や気持ちを表す文にする。抽象的な単語（効率、健康、便利）だけで並べない。
- 選択肢は、コンセプトの読み取りで特定した困りごとと叶えたい状態から作る。アプリと無関係な悩みを並べて、当てはまった感だけを作らない。
- 「まだわからない」「どれでもない」に当たる逃げ道を1つ用意する。選ばされ感を作らない。その場合のマッチ宣言は、無理に断定せず様子見の言い方に切り替える。
- 質問はマッチ宣言までに最大2問とする。3問以上は尋問のように感じられ、テンポも落ちる。2問聞いた場合は、2つの答えを組み合わせて返す。
- 選択のページには「次へ」ボタンを置かない。選択肢を押すこと自体が決定と前進を兼ねる。二度押し（選んでから次へ）はテンポを壊し、選んだ手応えも弱めるためである。
- 選んだ瞬間に、次の節の「押したら、褒める」の気持ちのいい反応（弾むアニメーション、称賛、触覚）を返し、その反応の余韻の中で自動で結果のページへ進む。反応を見せる目安は250〜400ミリ秒とし、待たされていると感じる長さにしない。連打による二重遷移は防ぐ。
- 逃げ道（まだわからない）も他の選択肢と同じ扱いにする。押したら同じ反応で、その答えに対応する結果のページへ進む。
- 選び直しは、結果のページから戻る操作でできるようにする。自動で進む代わりに、選択のページで長く考え直させる作りにしない。

### マッチ宣言のページ（結果のページ）

- 質問のページとは必ず分ける。このページには結果だけを置く。質問や選択肢を再掲しない。
- 主張は1つだけにする。「そんなあなたには、このアプリがぴったり」である。
- ユーザーが選んだ選択肢の言葉を、そのまま映して返す（例：「探すたびに時間がかかる」を選んだ人へは、その言葉を受けて「探す時間に困っているあなたには」と返す）。自分の言葉で言い直されたと感じさせることが、ぴったり感の正体である。
- ぴったりの根拠は、その悩みや希望に直接効くアプリの強みを1つだけ挙げる。すべての機能を並べるページにしない。それは価値のページの役割である。
- 宣言の後に置く価値のページは、選んだ悩みや希望に対応する価値から先に並べ替える。本体の最初の提案や初期設定にも、選んだ内容を反映する。選ばせただけで何も変わらない流れにしない。
- 効果そのものを保証する言い方はしない（例：必ず痩せる、絶対に見つかる）。ぴったりなのはアプリの目的と使い方であり、結果の約束ではない。医療や金融など結果の断定が問題になる領域では、特にこの線を守る。
- 文言の型と例は [文言の手引き](references/copy-guide.md) を使う。ページの構成は [ページのパターン集](references/page-patterns.md) の「選択とマッチの流れ」を使う。

## 押したら、褒める（アニメーションと触覚で返す）

意味のある操作には、その場で返す。アニメーションのリアクション、言葉の称賛、触覚フィードバックの3点セットである。押したのに何も返らない操作を作らない。必須範囲の定義はこの節を正本とする。アニメーションの反応と触覚はすべての段階で必須とし、言葉の称賛は中と大で必須、小では短い受け取りの一言かアイコンの変化でよい（文としての称賛は任意）。

### 強さの3段階

- 小（通常の選択、次のページボタン）：押した要素が軽く弾むアニメーションと、短い受け取りの一言またはアイコンの変化と、いちばん軽い触覚を返す。
- 中（悩み・希望の選択への回答、試し操作の成功）：少し大きく弾むアニメーションと、したことを具体的に褒める一文と、成功の触覚を返す。マッチ宣言へつながる選択はここに入れる。
- 大（オンボーディングの完了、本体の最初の成功）：一度だけの祝いのアニメーションと、締めの称賛と、成功の触覚を返す。次の操作を塞がない長さに収める。
- すべての操作を大で返さない。全部が山場になると、完了の山場が埋もれる。強弱の配分は experience-balance スキルでも確認する。
- スキップと戻るには称賛も成功の触覚も付けない。中立の軽い反応だけにする。離れる操作を祝わないし、責める反応も付けない。

### 称賛の言葉

- 褒める対象を具体的にする。何をしたか、何を選んだかに触れる（例：教えてくれてありがとう、それがいちばん助かる使い方です）。「すごい」「えらい」だけの空の称賛を繰り返さない。
- 段階ごとに3通り以上の言い回しを用意し、同じ称賛を続けて出さない。言い回しの管理は状態として持ち、直前に使ったものを避ける。
- 語調は対象アプリの利用者に合わせる。落ち着いた道具のアプリで幼い褒め方をしない。強さは段階で変え、語調はアプリ全体でそろえる。
- 称賛は1回につき1文までとする。長く褒めるとテンポが止まる。

### アニメーションと触覚の実装条件

- 反応は押した直後に始める。体感で遅れを感じさせないこと。弾みの中心は200〜350ミリ秒、祝いでも800ミリ秒程度までに収め、その間も次の入力を受け付ける。
- 選択のページでは、反応が遷移を兼ねる。押す → 反応（250〜400ミリ秒） → 結果のページへ自動で進む、の順を守る。反応を省略して即座に切り替えると乱暴に感じ、長く見せると待たされる。結果のページでも、入場のアニメーションで反応の余韻をつなぐ。
- 触覚は意味のある押下にだけ付ける。選択、回答、試し操作の成功、主要なボタン、完了である。スクロールやスワイプそのもの、連続タップの途中には付けない。
- 触覚の種類は段階に対応させる。iOS では選択に UISelectionFeedbackGenerator、小に UIImpactFeedbackGenerator の light、中と大の成功に UINotificationFeedbackGenerator の success を使う。Android では performHapticFeedback と HapticFeedbackConstants、Flutter では HapticFeedback の selectionClick、lightImpact、mediumImpact、successNotification を使う。独自の長い振動パターンは作らない。
- 端末やOSの触覚設定を尊重する。システム側でオフの場合は無理に鳴らさない。振動の直接制御で設定を迂回しない。
- 動きを減らす設定が有効な場合は、弾みを短いフェードと文字の反応へ置き換える。フィードバックはアニメーションだけに寄せず、見た目の状態変化と言葉を必ず組にする。触覚が無い端末でも、反応が成立する状態にする。
- 詳細な段階表と文言例は [ページのパターン集](references/page-patterns.md) と [文言の手引き](references/copy-guide.md) を使う。

## 見やすさと演出を設計する

1ページ1主張を、見た目と動きで支える。

- テキストだけのページを作らない。すべてのページに視覚の主役（図形、アイコン、イラスト、画面モック、写真）を置く。視覚が主張を伝え、テキストはそれを支える。
- 図形やアイコン、アニメーションをふんだんに使うが、1ページの主役は1つに絞る。複数の強い演出を同じページで競わせない。
- すべてのページに何かしらのアニメーションを付ける。静止したページを作らない。構成は次の2層とする。詳細は [ページのパターン集](references/page-patterns.md) の「全ページのアニメーション」を使う。
  - 主役のアニメーション：そのページで目立たせたいもの（主張を表す図形、ステップの番号、選ばせたい選択肢、押させたいボタン）に付ける、意味のある動き。何を目立たせ、何を伝えるための動きかを、ページ地図に必ず書く。
  - 常時のアニメーション：背景の図形が小さく震える、ゆっくり浮く、呼吸するように伸縮するなど、ページの空気を作るごく控えめな動き。ノイズにならない範囲に抑える。
- 常時のアニメーションの上限を守る。同時に動く常時アニメーションは1ページに2要素まで。振れ幅は小さく（移動は数ピクセル程度、回転は1〜2度程度、拡大縮小は数パーセント程度）、周期はゆっくり（2〜4秒程度）とし、要素同士で同期させない。色が激しく変わる動き、点滅、速い振動はノイズとして禁止する。
- 真剣なページ（権限の理由、同意、支払い、個人情報の入力など）では、常時のアニメーションを止め、主役も短いフェードの入場だけにする落ち着いた形を認める。全ページアニメーションの目的は空気を作ることであり、信頼を損なう場面では静けさ自体がその役割を果たす。
- 強弱の差で目立たせる。主役のアニメーションは常時のアニメーションより明確に強くし、常時の側は主役を引き立てる背景に徹する。全部が同じ強さで動くと、目立たせたいものが埋もれる。
- 動きの種類は意味に合わせる。震える動きは寒さや緊張やワクワクの震え、浮く動きは軽さ、脈打つ動きは生きている感じや注目、描かれる動きは手順の進行、のように、動き自体が主張の手がかりになるものを選ぶ。意味と無関係な動きをランダムに割り当てない。
- 次へ進む操作を遅らせる演出は入れない。アニメーションは割り込み可能にし、表示中でも操作を受け付ける。
- 見出しは1行、補足は最大2行とし、文字サイズとコントラストは本体より大きく読みやすくする。1ページの情報量は、3秒で全体が把握できる量に収める。
- 進捗は窓ドットで示す。総ページ数を直接数えさせない。何ページもあると思われると、内容を読む前にうっとおしく感じて離脱につながるためである。詳細な仕様は [ページのパターン集](references/page-patterns.md) の「進捗の示し方（窓ドット）」を使う。
  - 同時に見えるドットは最大5つまでとする。総ページ数が5以下の場合は、通常のドットで全ページを示してよい。
  - 現在のページを中心に窓がスライドし、窓の端のドットは小さく表示する。先にまだページがあることと、前に戻れることだけが伝わる状態にする。
  - 1ページ進むごとにドットは必ず1つ動く。複数ページで同じドットが光り続ける圧縮ドットは使わない。進んでも動かない表示は、止まったように見えるためである。
  - 「3 / 10」のような数字の進捗や、総ページ数の表記は出さない。
  - ドットは表示専用とし、タップで特定ページへジャンプさせない。窓がずれる表示でジャンプ先を示すと、位置の対応が壊れるためである。
  - 読み上げでは、総数ではなく現在の章やステップの名前で現在地を伝える。視覚の窓ドットと読み上げの意味が食い違わないようにする。
- 次へ進む操作は、説明のページではどこでもタップやスワイプで進める。戻る操作とスキップも同じ場所に常に置く。スキップを隠さない。選択のページは例外とし、「次へ」ボタン自体を置かず、選択肢を押すことで進む（「悩み・希望を選ばせて、ぴったりで返す」を使う）。
- テンポの設計は [ページのパターン集](references/page-patterns.md) と experience-balance スキルで確認する。短いページをリズムよく並べ、山場の前後に呼吸を置く。同じ強さのページを連続させない。

## インタラクティブな要素を入れる

受け身で見せるだけのオンボーディングにしない。適宜、選択や回答をさせる。

- インタラクションの種類は次から選ぶ。
  - 悩み・希望の選択：困りごとや叶えたい状態を選ばせ、マッチ宣言で返す（「悩み・希望を選ばせて、ぴったりで返す」の流れ。標準で入れる）
  - 選択：目的、経験、好み、気になる場面から1つ選ばせる（2〜4択）
  - 回答：簡単な質問に答えさせる（自由記述は求めない）
  - 試し操作：本体の核となる操作を、オンボーディングの中で小さく体験させる
  - 診断：回答からタイプやおすすめを返し、後のページや本体の初期状態に反映する
- インタラクションは、悩み・希望の選択を含めて最低2回入れる。1回だけの場合は、その1回が後の内容を変えるものであることを確認する。
- すべての意味のある押下に、「押したら、褒める」（本編の定義）の返しを段階に合わせて行う。アニメーションと触覚は全段階で必須、称賛の文は中と大で必須、小では受け取りの印でよい。
- すべての質問と選択には、答えた先の変化を用意する。後のページの文言、すすめ方、初期設定、最初の提案のいずれかが、答えによって変わること。答えがどこにも使われない質問は入れない。
- 1ページで聞くことは1つだけにする。複数の質問を1ページに並べない。
- 選択肢は大きくタップしやすくする。選び直しは、結果のページから戻る操作でできるようにする。答えたくない人には、逃げ道の選択肢かスキップで先へ進ませる。
- 質問のページには「次へ」ボタンを置かない。選択肢を押したら、気持ちのいい反応を返して自動で次のページへ進む。自動遷移の行き先は、残りの質問がある場合は次の質問のページ、質問が残っていない場合は結果のページ（マッチ宣言）と定義する。2問ある場合に、1問目から宣言へ直行しない。
- 結果は質問とは別ページで返す。タイプ名、診断の返し、マッチ宣言はすべて結果のページの内容とする。質問のページで返すのは、押した瞬間の短い反応（弾み、称賛、触覚）だけであり、結果の文章を同居させない。無反応で次へ送らない。
- 試し操作は、本物の操作のミニ版にする。操作の練習に見えるが本体と無関係な遊びは入れない。試し操作の成否の結果は、試し操作のページとは分けて、結果のページで示す（表示は常に結果のページが担う）。データとしての結果は本体の最初の状態へ引き継ぐ。

## 文言とテンポの仕上げ

- 見出しは主張そのものの一文にする。詳しい書き方は [文言の手引き](references/copy-guide.md) を使う。
- 補足文は短く、専門用語や機能名の羅列を避ける。ユーザーの場面と言葉で書く。
- 3ステップの見出しは、動詞で始める。何をするのかが読んだ瞬間にわかる形にする。
- ページごとの滞在時間の目安は、通常ページで3〜5秒、インタラクションのページで5〜10秒とする。全体の完了時間の目安は60〜120秒とし、標準フローでは90秒前後を狙う。優先順位は、1ページ1主張の分割を総時間より優先する。目安を超える場合は、ページの統合ではなく主張の削減で調整する。数値の正本は [ページのパターン集](references/page-patterns.md) の「テンポの設計」とし、本文と食い違う場合はパターン集を優先する。
- 最後の接続ページでは「始める」だけにしない。ユーザーが本体で最初にやることを一言で添え、押した先の画面を予告する。

## 実装する

設計したページ地図と文言を、対象アプリの技術に合わせて実装する。

- ページ遷移は、対象プラットフォームの標準的なページ送り（Flutter の PageView、SwiftUI の TabView、Jetpack Compose の HorizontalPager、React Native の PagerView など）で実装する。独自のジェスチャー処理は作らない。
- オンボーディングの状態は、現在のページ、回答、完了状態を分けて持つ。回答は本体の初期設定へ渡せる形で保存する。
- 完了したことは端末に保存し、次回起動では表示しない。オンボーディングの版が変わった場合は、版番号で再表示の要否を判断する。
- 権限やアカウントのページでは、システムのダイアログを出す前にアプリ内の説明ページを通し、拒否された場合の再案内の導線を用意する。
- 触覚はOS標準のフィードバック機構で実装し、端末の設定に従う。称賛の言い回しは使い回しを避けるため、直前に出した称賛を状態として覚える。
- 計測は、ページごとの表示、離脱、スキップ、回答をイベントとして記録する。個人を特定できる内容は計測しない。悩み・希望の選択内容そのものは、本体の初期設定に使う範囲でのみ保存し、計測の識別子と結び付けない。
- 悩み・希望の選択内容は、健康や生活の事情など機微な内容になり得る。保存は端末内を原則とし、端末の外へ送る場合は、その目的を本人へ示し、初期設定に必要な範囲を超えて保持しない。アカウント削除やデータ消去の対象に含める。
- アニメーションは transform と opacity を中心に実装し、画面外のページでは止める。常時のアニメーションは、動きを減らす設定が有効な場合は止め、主役のアニメーションは短いフェードへ置き換える。
- アクセシビリティを確認する。読み上げの順序は見出し → 補足 → 視覚の説明 → 操作の順にし、文字サイズの拡大とコントラスト、動きを減らす設定に対応する。選択のページでは、選択肢を押すと自動で進むことを読み上げでも伝え、結果のページへ移動したことを見出しで示す。
- 多言語対応する場合は、文言の文字数の伸びを見込んでレイアウトを組む。見出しが2行に膨らむ言語でも、主張が1つであることを保つ。

## 検証してから渡す

実装後に、4つの達成条件と絶対のルールを [出荷前のチェックリスト](references/checklist.md) で確認する。

- ページごとの主張が1つであることを、全ページで数えて確認する。2つ以上あるページが残っていたら、分割してから出荷する。
- スリーステップがちょうど3つであることと、3つで基本的な使い方がわかることを確認する。
- 人間に触ってもらえる場合は、オンボーディングの直後に3つだけ聞く。何のためのアプリか、最初に何をするか、使ってみたいか。その答えで4条件の達成を判断する。AIの自己評価だけで達成にしない。
- 離脱が多いページや滞在が長いページがあれば、主張の詰め込み、文言の長さ、演出の遅さを疑い、ページ地図へ戻って直す。
- 計測の結果と人間の観察は、案件の記録に残す。

## コンセプト達成を最終照合する

案件を閉じる前に、当初のコンセプトと最終成果を項目ごとに突き合わせる。concept-driven-ux スキルと連携する場合は、その [コンセプト達成の最終照合](https://github.com/TaigaShinohara/concept-driven-ux/blob/main/skills/concept-driven-ux/references/concept-check.md) の様式を使う。連携しない場合は、次を表にして記録する。

- コンセプトの要素（誰が、どんな場面で、何をして、どんな状態や気持ちになるか）ごとの、最終成果での実現内容と根拠（動作確認、人間の観察のどれで確かめたか）と判定（実現／部分的に実現／未実現／未確認）
- 4つの達成条件ごとの判定と根拠

未実現の要素があれば案件を完了にせず、戻し先（コンセプトの読み取り、ページ地図、文言、演出）を決めて差し戻す。人間の体験確認がまだの要素は「未確認」として残し、AIの照合や動作確認だけでコンセプトを達成したと扱わない。

## 最後に簡潔に報告する

届けたい体験、読み取ったコンセプトと根拠、ページ地図（ページ数と各ページの主張）、スリーステップの内容、入れたインタラクションとその答えの使い道、テンポと完了時間の目安、検証の結果と未確認の範囲を日本語で伝える。設計・実装・動作・試用準備・人間の体験の確認状況を分け、成果物や根拠へリンクする。Git管理下ではコミットIDまたは未コミットの理由と残存差分も示す。

- 設計成果物の独立審査と差し戻しは independent-review スキルの審査手順に従う。
